# 会話情報RAGシステム 設計書

## 1. システム目的
営業と取引先の会話情報から、取引先が何を求めているかを効率的に検索・抽出するRAGシステムを構築する。

## 2. システム構成

### 2.1 主要コンポーネント
```
[既存DB] → [データ取得層] → [前処理層] → [ベクトル化層] → [ベクトルDB]
                                                                    ↓
[ユーザー] → [クエリ処理] → [検索エンジン] ←-------------------[ベクトルDB]
                                   ↓
                            [LLMによる回答生成] → [回答出力]
```

### 2.2 技術スタック候補
- **ベクトルDB**: Milvus
- **Embedding Model**: Qwen3-embedding:8b
- **LLM**: Qwen3-32B-AWQ
- **RAGフレームワーク**: LlamaIndex / LangChain

## 3. データ処理設計

### 3.1 インデックス作成フロー

#### 3.1.1 データ取得
- 既存DBから文字起こし情報を取得
- 取得単位: 1会話セッション = 1レコード

#### 既存DBスキーマ
##### 会話セッション
- uid(会話セッションのユニークID)
- 営業担当者名
- 会社名
- 拠点名
- 部署名
- 取引先担当者名
- 会話情報(発話情報のリスト)
- 要約

##### 発話情報(話者不明)
- 発話開始時間
- 発話終了時間
- 発話内容

##### 要約
要約の構成
```
□全体概要
<全体概要内容>

□トピック別要約
Topic1: <Topic1のタイトル>
・<Topic1の要約内容>
・<Topic1の要約内容>
Topic2: <Topic2のタイトル>
・<Topic2の要約内容>
・<Topic2の要約内容>

□決定事項
・<決定事項>
・<決定事項>
```

#### 3.1.2 チャンク分割戦略
**戦略1: 会話情報ベース**
- 発話単位でチャンク化
- 前後N発話をコンテキストとして含める（オーバーラップ）
- チャンクサイズ目安: 3-5発話単位

**戦略2: トピック別要約ベース**
- 要約のトピック単位でチャンク化
- 全体概要を各チャンクのメタデータに含める

**戦略3: ハイブリッド**
- 会話情報と要約の両方を別々にインデックス化
- 検索時に両方から情報を取得

#### 3.1.3 メタデータ設計
各チャンクに付与するメタデータ:
```json
{
  "uid": "会話セッションのユニークID",
  "営業担当者名": "担当者A",
  "会社名": "株式会社B",
  "拠点名": "東京本社",
  "部署名": "営業部",
  "取引先担当者名": "担当者C",
  "発話時間範囲": "00:05:30 - 00:07:15",
  "チャンク種別": "conversation|summary|decision",
  "トピック": "Topic1タイトル",
  "全体概要": "この会話の全体概要テキスト"
}
```

#### 3.1.4 ベクトル化
- Embeddingモデルで各チャンクをベクトル化
- 日本語対応モデルを選択（多言語モデルまたは日本語特化モデル）

### 3.2 検索設計

#### 3.2.1 検索クエリ前処理
1. ユーザークエリを受け取る
2. 必要に応じてクエリ拡張（関連語句の追加）
3. フィルタ条件の抽出（会社名、担当者名など）

#### 3.2.2 検索戦略
**ベクトル検索**
- セマンティック検索で関連チャンクをTop-K取得（K=5-10）
- メタデータフィルタリング適用

**ハイブリッド検索（推奨）**
- ベクトル検索 + キーワード検索の組み合わせ
- 重み付けスコアリング（α * ベクトルスコア + (1-α) * キーワードスコア）

**リランキング**
- 検索結果を再スコアリング
- クロスエンコーダーモデルまたはLLMによる関連度評価

#### 3.2.3 コンテキスト構築
1. 取得したチャンクを関連度順にソート
2. トークン制限内で複数チャンクを結合
3. メタデータ情報を構造化して含める
4. 元の会話の時系列を考慮した並び替え

### 3.3 回答生成設計

#### 3.3.1 プロンプト設計
```
システムプロンプト:
あなたは営業支援AIです。取引先との会話記録から、
取引先のニーズや要望を分析して回答してください。

コンテキスト:
{検索で取得したチャンク情報}
- 会社名: {会社名}
- 取引先担当者: {担当者名}
- 会話内容: {チャンク内容}
...

ユーザークエリ:
{ユーザーの質問}

回答形式:
- 取引先が求めていること
- 該当する会話の要点
- 情報源（会社名、日時、担当者）
```

#### 3.3.2 回答生成フロー
1. プロンプトにコンテキストとクエリを埋め込み
2. LLMに送信
3. 回答を受け取り、構造化
4. 情報源のトレーサビリティを付与

## 4. 検索パターン

### 4.1 主要な検索ユースケース

**パターン1: 特定取引先のニーズ抽出**
- クエリ例: 「株式会社Bは何を求めていますか？」
- フィルタ: 会社名 = "株式会社B"
- 検索対象: 全チャンク種別

**パターン2: 業界・課題横断検索**
- クエリ例: 「コスト削減に関心がある取引先は？」
- フィルタ: なし
- 検索対象: 主に要約チャンク

**パターン3: 決定事項の確認**
- クエリ例: 「株式会社Bとの決定事項は？」
- フィルタ: 会社名 + チャンク種別="decision"
- 検索対象: 決定事項チャンク

**パターン4: 営業担当者別の分析**
- クエリ例: 「担当者Aが対応した案件で頻出する要望は？」
- フィルタ: 営業担当者名 = "担当者A"
- 検索対象: 要約チャンク

**パターン5: 時系列分析**
- クエリ例: 「株式会社Bのニーズの変化は？」
- フィルタ: 会社名 + 時系列ソート
- 検索対象: 全チャンク種別（時系列順）

## 5. データ更新設計

### 5.1 インクリメンタル更新

### 5.2 再インデックス
- チャンク戦略変更時
- Embeddingモデル変更時
- 全データの再ベクトル化

## 6. 評価指標

### 6.1 検索品質評価
- **Precision@K**: 上位K件の適合率
- **Recall@K**: 上位K件の再現率
- **MRR (Mean Reciprocal Rank)**: 最初の適合文書の順位
- **NDCG**: 順位を考慮した評価指標

### 6.2 回答品質評価
- **正確性**: 回答が取引先のニーズを正しく表現しているか
- **完全性**: 必要な情報が網羅されているか
- **トレーサビリティ**: 情報源が明確か
- **ユーザー満足度**: 実際のユーザーフィードバック

### 6.3 評価データセット作成
- 典型的な質問と期待回答のペアを作成
- 営業担当者によるラベリング
- 継続的な評価とチューニング

## 7. システムインターフェース設計

### 7.1 検索API
```
エンドポイント: POST /api/search

リクエスト:
{
  "query": "検索クエリ",
  "filters": {
    "会社名": "株式会社B",
    "営業担当者名": "担当者A"
  },
  "top_k": 5,
  "search_mode": "hybrid"
}

レスポンス:
{
  "answer": "生成された回答",
  "sources": [
    {
      "uid": "xxx",
      "会社名": "株式会社B",
      "取引先担当者名": "担当者C",
      "チャンク内容": "...",
      "関連度スコア": 0.95,
      "発話時間範囲": "00:05:30 - 00:07:15"
    }
  ],
  "search_time_ms": 230
}
```

### 7.2 インデックス管理API
```
エンドポイント: POST /api/index/add
- 新規会話データの追加

エンドポイント: POST /api/index/update
- 既存データの更新

エンドポイント: DELETE /api/index/delete
- データの削除

エンドポイント: POST /api/index/rebuild
- 全インデックスの再構築
```

## 10. システムフロー図

### 10.1 インデックス作成フロー
```
[開始]
  ↓
[既存DBから会話データ取得]
  ↓
[会話情報と要約を分離]
  ↓
[チャンク分割処理]
  ├─ 会話情報チャンク（発話単位）
  └─ 要約チャンク（トピック単位）
  ↓
[メタデータ付与]
  ↓
[Embeddingモデルでベクトル化]
  ↓
[ベクトルDBに保存]
  ↓
[完了]
```

### 10.2 検索・回答生成フロー
```
[ユーザークエリ入力]
  ↓
[クエリ前処理・フィルタ抽出]
  ↓
[クエリのベクトル化]
  ↓
[ベクトルDB検索]
  ├─ セマンティック検索
  └─ メタデータフィルタリング
  ↓
[リランキング]
  ↓
[コンテキスト構築]
  ↓
[プロンプト生成]
  ↓
[LLMによる回答生成]
  ↓
[回答 + 情報源を返却]
  ↓
[完了]
```
